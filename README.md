# CICD-code

ชุดไฟล์สำหรับทำ CI/CD ให้โปรเจกต์ที่รันด้วย Docker Compose เอามาจากที่ใช้จริงกับแชทบอทของโรงพยาบาลธรรมศาสตร์ฯ อันนี้เพื่อให้พี่โอ๊ค พี่จ๋า พี่แป้งปรับให้ใช้กับโปรเจกต์อื่นได้

ช่วย 2 เรื่อง

- **ตรวจโค้ดให้อัตโนมัติ (CI)** ทุกครั้งที่มีคนส่งโค้ดขึ้น GitHub จะมีการตรวจว่าโค้ดพังไหม build ได้ไหม มีรหัสผ่านหลุดเข้ามาไหม ถ้าไม่ผ่านจะเอาเข้าโค้ดหลักไม่ได้
- **อัปเดตระบบด้วยคำสั่งเดียว (CD)** บนเครื่องเซิร์ฟเวอร์พิมพ์คำสั่งเดียว ระบบจะดึงโค้ดใหม่มาใช้ ถ้าเวอร์ชันใหม่มีปัญหาจะถอยกลับไปเวอร์ชันเดิมให้เอง


| ไฟล์ | ใช้ทำอะไร |
|---|---|
| `templates/ci.yml` | รายการตรวจที่ GitHub จะรันให้ทุกครั้ง (ต้นแบบ ต้องแก้ path ให้ตรงโปรเจกต์) |
| `scripts/deploy.py` | สคริปต์อัปเดตระบบบนเครื่องเซิร์ฟเวอร์ |
| `scripts/check_migrations.py` | ตรวจว่าไฟล์เปลี่ยนโครงสร้างฐานข้อมูล (Alembic) ไม่ไปแตะตารางของระบบอื่น ใช้เฉพาะโปรเจกต์ที่ใช้ฐานข้อมูลร่วมกับคนอื่น |
| `examples/tuh-chatbot-ci.yml` | ไฟล์ CI ตัวจริงของแชทบอท ไว้ดูเป็นตัวอย่าง |

## ภาพรวมการทำงาน

```
แก้โค้ด → ส่งขึ้น GitHub (branch ใหม่) → เปิด Pull Request
      → GitHub ตรวจโค้ด (5–10 นาที)
      → ผ่านครบ กด Merge เข้า main
      → บนเครื่องเซิร์ฟเวอร์: python deploy.py
      → ระบบใช้เวอร์ชันใหม่ (หรือถอยกลับเองถ้ามีปัญหา)
```

ทำไมขั้นสุดท้ายยังต้องกดเอง: เครื่องเซิร์ฟเวอร์ของโรงพยาบาลอยู่ในเครือข่ายภายใน GitHub เข้ามาสั่งไม่ได้ ให้เครื่องเป็นฝ่ายไปดึงโค้ดเองปลอดภัยกว่า

## เริ่มใช้กับโปรเจกต์ของพี่ๆ

สิ่งที่ต้องมีก่อน: โปรเจกต์อยู่บน GitHub และรันด้วย `docker compose` ได้แล้ว

**1. ใส่ไฟล์ตรวจโค้ด**

copy `templates/ci.yml` ไปไว้ที่ `.github/workflows/ci.yml` ในโปรเจกต์ แล้วแก้บรรทัดที่มีคำว่า `แก้` ให้ตรงกับโฟลเดอร์ของโปรเจกต์ ส่วนไหนไม่มีก็ลบทิ้ง เช่น ไม่มีหน้าเว็บก็ลบส่วน `web`

ส่งขึ้น GitHub แล้วเปิดแท็บ **Actions** ดูว่าขึ้นเครื่องหมายถูกสีเขียวครบไหม ถ้าแดงให้กดเข้าไปดูว่าข้อไหนไม่ผ่าน

**2. ใส่สคริปต์อัปเดตระบบ**

copy `scripts/deploy.py` (และ `scripts/check_migrations.py` ถ้าจะใช้) ไปไว้ที่โฟลเดอร์ `scripts/` ของโปรเจกต์ เปิด `deploy.py` แล้วแก้ค่าในส่วน "ตั้งค่า" ด้านบนไฟล์

| ค่า | ใส่อะไร |
|---|---|
| `HEALTH_URL` | ลิงก์ที่ใช้เช็กว่าระบบยังทำงาน เช่น `http://127.0.0.1:8000/health` ไม่มีก็เว้นว่าง |
| `HEALTH_TIMEOUT` | ระบบใช้เวลาเปิดนานสุดกี่วินาที (ค่าเริ่มต้น 300) |
| `ALEMBIC_SERVICE` | ชื่อ service ที่ใช้ Alembic เช่น `backend` ไม่ใช้ก็เว้นว่าง |
| `PRE_CHECK` | คำสั่งที่อยากให้รันก่อนอัปเดต เช่นตัวตรวจ migration ไม่มีก็เว้นว่าง |
| `HISTORY_FILE` | ไฟล์เก็บประวัติการอัปเดต |

ชื่อโปรเจกต์และรายชื่อ service สคริปต์อ่านจาก `docker-compose.yml` เอง ไม่ต้องใส่

**3. ล็อกไม่ให้เอาโค้ดที่ไม่ผ่านการตรวจเข้า main**

ที่หน้า GitHub ของโปรเจกต์ ไปที่ **Settings → Branches → Add branch ruleset** แล้วตั้งตามนี้

- Ruleset Name: `protect-main` และ Enforcement status: **Active**
- Target branches: Add target → **Include default branch**
- ติ๊ก **Restrict deletions** และ **Block force pushes**
- ติ๊ก **Require a pull request before merging** ถ้าทำคนเดียวให้ตั้ง Required approvals เป็น 0 (GitHub ไม่ให้อนุมัติงานตัวเอง)
- ติ๊ก **Require status checks to pass** แล้วกด Add checks เลือกทุกข้อที่ขึ้นมา (ต้องเคยรันข้อ 1 สำเร็จมาก่อน ชื่อถึงจะขึ้นให้เลือก)
- กด **Create**

**4. เตรียมเครื่องเซิร์ฟเวอร์**

ใช้โฟลเดอร์แยกสำหรับระบบจริง อย่าใช้โฟลเดอร์เดียวกับที่แก้โค้ด

```bash
git clone https://github.com/<ชื่อบัญชี>/<ชื่อโปรเจกต์>.git
cd <ชื่อโปรเจกต์>
# วางไฟล์ .env (รหัสผ่านต่าง ๆ) เอง — ไฟล์นี้ไม่อยู่ใน GitHub
python3 scripts/deploy.py --check   # ลองซ้อม ไม่กระทบระบบที่ใช้อยู่
python3 scripts/deploy.py           # อัปเดตจริง
```

## อัปเดตระบบครั้งต่อ ๆ ไป

1. แก้โค้ดบน branch ใหม่ แล้วส่งขึ้น GitHub
2. เปิด Pull Request รอตรวจผ่าน แล้วกด Merge
3. ที่เครื่องเซิร์ฟเวอร์ เข้าโฟลเดอร์โปรเจกต์ แล้วพิมพ์ `python3 scripts/deploy.py`

ขึ้น ✅ แปลว่าเสร็จ ระหว่างสลับเวอร์ชันระบบจะหยุดไม่ถึงนาที

## ถ้าอัปเดตไม่ผ่าน

สคริปต์จะถอยกลับไปเวอร์ชันเดิมให้เองและบอกว่าไม่ผ่านเพราะอะไร ระบบยังใช้งานได้ตามปกติ ดูรายละเอียดเพิ่มด้วย

```bash
docker compose logs --tail 100
```

แก้โค้ดให้เรียบร้อย ส่งขึ้นใหม่ตามขั้นตอนเดิม แล้ว deploy อีกครั้ง

ถ้าสคริปต์หยุดพร้อมบอกว่า "ฐานข้อมูลยังไม่อยู่ที่ migration ล่าสุด" แปลว่ามีการเปลี่ยนโครงสร้างฐานข้อมูล สคริปต์จะไม่ทำส่วนนี้เอง ให้คนดูไฟล์ migration ก่อน แล้วรันคำสั่งที่สคริปต์บอก จากนั้น deploy ใหม่

## คำถามที่เจอบ่อย

**ทำไมไม่ให้ GitHub อัปเดตเซิร์ฟเวอร์ให้เองเลย**
ทำได้ด้วยการติดตั้งตัวรับงานของ GitHub (self-hosted runner) ไว้บนเครื่อง แต่ถ้าโปรเจกต์เป็น public คนนอกสามารถส่งโค้ดมาให้รันบนเครื่องในโรงพยาบาลได้ จึงไม่แนะนำ

**`--check` ต่างจากรันปกติยังไง**
`--check` ทำทุกขั้นจนถึง build เสร็จ แต่ไม่สลับไปใช้เวอร์ชันใหม่ ใช้ซ้อมหรือเช็กว่าทุกอย่างพร้อมได้ตลอด ไม่กระทบคนที่ใช้งานอยู่

**ประวัติการอัปเดตดูที่ไหน**
ไฟล์ที่ตั้งไว้ใน `HISTORY_FILE` (ค่าเริ่มต้น `~/deploy-history.log`) บรรทัดละครั้ง บอกเวลา เวอร์ชัน และผล ใช้เป็นหลักฐานการเปลี่ยนแปลงระบบ (เช่นตาม ISO 27001) ได้

**ใช้บน Windows ได้ไหม**
ได้ แต่ Docker Desktop บน Windows จะไม่เปิดเองหลังเครื่องรีบูตถ้ายังไม่มีคน login ระบบจริงควรอยู่บนเครื่อง Linux

## ข้อควรระวัง

- ห้ามใส่รหัสผ่านหรือข้อมูลลับลงในไฟล์ที่ส่งขึ้น GitHub ให้อยู่ใน `.env` บนเครื่องเท่านั้น ถ้าเผลอหลุดไปแล้วต้องเปลี่ยนรหัสทันที ลบออกจาก GitHub อย่างเดียวไม่พอ
- อย่าสั่ง `docker compose down -v` บนเครื่องจริง คำสั่งนี้ลบข้อมูลทิ้งทั้งหมด

## ทดสอบแล้วอะไรบ้าง

- `deploy.py`: ซ้อมแบบ `--check` กับแชทบอทจริง ผ่าน และลองกับโปรเจกต์จำลองทั้งกรณีอัปเดตสำเร็จ และกรณีเวอร์ชันใหม่พังแล้วถอยกลับเอง ผ่านทั้งสองกรณี
- `check_migrations.py`: ตรวจ migration จริงของแชทบอท 11 ไฟล์ ผ่าน และจับไฟล์ทดสอบที่แอบแตะตารางคนอื่นได้ครบ
- `templates/ci.yml`: ดัดแปลงมาจาก `examples/tuh-chatbot-ci.yml` ที่ใช้งานจริงอยู่ แต่ตัวต้นแบบเองยังไม่เคยรันบน GitHub ตรง ๆ ครั้งแรกที่ใช้ให้ดูผลในแท็บ Actions
